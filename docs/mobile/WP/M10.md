# M10 · Értesítések (`inbox`): PR, CI and relay events in one place

**Goal.** One list of what happened, with phone notifications for what matters: a PR opened or reviewed, CI
failed or green, a release ready (M9), a note from another device (M6), and relay events (a PC came online, a
screenshot is ready). Answer D-11 first. The recommended default is C: polling now, push later.

## Build (D-11 = A / C)

- `kit-core`: the event model, deduplication by id, and rules for what notifies (CI failure: always; a green build
  after a failure: yes; a comment: only on PRs the user opened), with tests.
- `kit`: a WorkManager job every 15 min (the Android minimum) calling `GET /notifications` (with
  `If-Modified-Since`, honouring `X-Poll-Interval`) and `GET /repos/{r}/actions/runs?per_page=10`. While the relay is
  connected, relay events come in live.
- `feature-inbox`: the list grouped by day, with filters (CI · PR · relé · jegyzet). A tap opens the GitHub page or the
  feature. Mark read syncs to GitHub (`PATCH /notifications/threads/{id}`).
- Notification channels: "CI", "PR", "Relé", "Frissítés", each switchable in M1.

## Tests (cloud)

The notification rules on fixtures, the dedupe across polls, and the backoff on 403 rate limiting.

## As built (2026-11-06, D-11 = C, stage BETA)

**The rules are kit-core's `Inbox.kt`** (16 JVM tests in `InboxTest`); the Android side only moves bytes.

- **Event model.** `InboxEvent` with a stable id that is the dedupe key across polls and sources:
  `gh:<thread>:<updated_at>` (a GitHub notification thread; its newer state replaces the older one in the list),
  `run:<id>:<attempt>` (an Actions run), `rel:<code>` (a release), `note:<sha>` (a mobile-log commit),
  `relay:<pc>:<id>` (a relay notice), `board:<id>` (a file put on the board from the PC), `pc:<pc>:<ms>` (the PC back).
  `InboxState` keeps the last 300 events, every id ever seen (2000), each workflow + branch's last outcome, the
  per-source first-poll baseline, the backoff and GitHub's `X-Poll-Interval`; JSON in `filesDir/inbox.json`.
- **What notifies.** A CI failure (`failure`, `timed_out`, `startup_failure`): always. A green run: only after a failure
  of the same workflow on the same branch (green after green is not listed at all; cancelled / skipped say nothing).
  GitHub threads: `review_requested`, `author` (activity on your own PR / issue), `mention`, `team_mention`, `assign`,
  `security_alert` ring; `comment`, `subscribed`, `state_change` are listed only; `CheckSuite` / `ci_activity` and
  `Release` threads are left to the runs and release sources. A release newer than the installed build rings even on
  the first poll (`urgent`). A note on `mobile-log` from another device rings. **The first answer of each source only
  fills the list**, so installing does not ring old news. Data branches (`city-pages`, `mobile-log`, `solomon-data`)
  produce no CI events.
- **Polling (kit `GitHub.poll`).** A WorkManager periodic job every 15 minutes (`vrg-inbox-poll`, network required),
  plus one round when the app comes on screen if the last is 5+ minutes old; ⟳ / pull-to-refresh asks at once but not
  more often than `max(60 s, X-Poll-Interval)`. Four conditional GETs: `/repos/{r}/notifications` (needs the token;
  repo-scoped rather than the user's whole `/notifications`, as the app works with the one repo),
  `/actions/runs?per_page=10`, `/releases/latest`, `/commits?sha=mobile-log&per_page=10`. `GitHub.poll` keeps ETag,
  Last-Modified and the body per URL in `cacheDir/github-poll/` (cleared on sign-out), so the worker's fresh process
  still sends `If-None-Match` / `If-Modified-Since` and a quiet repo answers 304 for free; a 304 skips the parse.
- **Backoff.** A 403 / 429 that is a rate limit (primary spent, `Retry-After`, or GitHub's secondary-limit message)
  stops the round and waits GitHub's time, never less than 1, 2, 4 … 60 minutes for the 1st, 2nd, 3rd … in a row; the
  worker skips rounds until then. A plain 403, or a 404 (no release yet), is not a limit; the other sources go on.
- **Relay events** (live while the trusted link is up): the relay's new `notify` (`relay-notify.js`: a PC tool sends
  `POST /notify` from this PC only, an app connected from this PC sends `{type:'notify'}`; the relay keeps the last 30
  for a day, at most 20 a minute, and `notify.list {after}` after a reconnect brings the missed ones), a board file
  `from: pc` (M12), and "<PC> újra vonalban" when the phone had not seen that PC for 10+ minutes.
  `node Planner/projects/varler-planner/tools/relay-notify.js "Cím" "szöveg" [--level good|bad] [--link https://…]`
  is the command line for scripts and START. Tested by `Mobile/tests/relay-notify.js` (44).
- **Channels** (kit `VrgNotify`): CI, PR, Relé, Frissítés, Jegyzet (the WP named four; notes got their own so they can
  be silenced apart). Beállítások (M1) → Értesítések lists them with Android's on/off and opens Android's page for the
  one tapped; the switch is Android's, not a second copy in the app. A tap on a notification goes to
  `vrg://inbox/open?id=…`: the event is marked read (plus `PATCH /notifications/threads/{id}` for a thread) and its page
  opens in a Custom Tab, or its feature (Frissítés, Átadás, Indítópult). No phone notification while the list is on screen.
- **Permission.** Android 13+'s `POST_NOTIFICATIONS` is asked only from the Értesítések screen ("Engedélyezés"), with
  "Android beállítások ›" once Android stops showing the dialog; without it the list fills and nothing rings.
- **Notes now name their device.** `NoteWriter.send(…, device = Build.MODEL)` writes
  "mobile-log: <day> [tag] jegyzet (<model>)", so the inbox skips this phone's own notes. Two phones of one model cannot
  be told apart; notes from older builds (no model) count as another device's.
- **Repo-name (guest) access:** no token, so no notification threads; runs, release and notes still poll.
- **Not built from the goal:** "a screenshot is ready" is not an inbox event: it only ever answers the phone's own 📸
  request on the open Légegér screen.

### D-11 B, the push service: a later WP

Not built. The slot is left: `InboxSource.PUSH`, and `InboxFeature.take(events, source)` is the one door every source
goes through. A push WP (e.g. a GitHub Action calling ntfy.sh, the phone subscribed to a private topic) would deliver
events **with the same ids** (`run:<id>:<attempt>`, `rel:<code>`, …), so whichever of push and poll arrives first wins
and the other is dropped by the dedupe (tested); the 15-minute poller stays as the fallback. It needs its own decisions
(the service, the topic secret, a foreground connection or FCM), so it gets its own WP and decision.

### What I could not verify here

- Nothing ran on a phone: the worker's real 15-minute rhythm, Doze / battery saver delaying it, the notifications'
  look, the channel switches, the permission dialog, the tap routing.
- **Android 15's background network block** (met in M6: a process kept alive behind the lock screen gets no network,
  yet WorkManager still runs workers in it) may make some rounds fail at once; the next round or opening the app
  catches up, but in that state a CI failure could arrive later than 15 minutes.
- Real GitHub answers: the parsers are tested on recorded shapes written from the API docs, not on answers fetched with
  the user's token (none here). Whether GitHub sends `X-Poll-Interval` / `Last-Modified` on the repo-scoped
  notifications endpoint, and the thread PATCH's 205, are unchecked.
- Relay events reach the phone only while the app's process lives and the relay link is up (no foreground service for
  the inbox); after a reconnect `notify.list` brings the PC's notices, but board files and "újra vonalban" are not replayed.
- `Mobile/mobile.cmd` (another session's uncommitted hunks) does not list `relay-notify.js` among its relay tests yet.
