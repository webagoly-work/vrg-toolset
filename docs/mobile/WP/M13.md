# M13 · Képernyő (`screen`): the PC's screen, live on the phone

**Goal.** See what is on the PC while away from it: a few frames a second, enough to read the screen and follow a
Planner or Kódváros view. With Légegér's pointer on the same screen, the phone can steer the PC while watching it.
Légegér's 📸 keeps working as it is; this is the moving version of it.

This uses the relay and needs M2 pairing. Traffic is plain HTTP, so on a shared network anyone can capture what is on
screen, client documents included: use a hotspot on a site.

## Measure first

The frame rate below is an estimate. Before building the phone side, run the capture loop alone on this PC and record
the real numbers here: frames a second, CPU, KB a frame at 1280 px. If it stays under 2 frames a second, stop and report
before going on.

## How it works

- **Capture.** One long-running PowerShell process, not one per frame, keeps a `Bitmap` and loops over `CopyFromScreen`,
  scales to at most 1280 px on the long side, encodes JPEG (quality about 55) and writes length-prefixed frames to
  stdout. It starts with the first viewer and stops with the last. Windows only in M13; on other systems the relay
  answers with a clear refusal, and 📸 still works there.
- **The cursor.** `CopyFromScreen` leaves the mouse cursor out, and Légegér is useless without it. The loop draws it
  into each frame (`GetCursorInfo` + `DrawIcon`).
- **What to show.** `screen` (one monitor, picked in the view; `VirtualScreen` would shrink a multi-monitor desk to
  nothing) or `window` (the foreground window, as 📸 does). Changing the mode does not need a new ticket.
- **Unchanged frames are skipped**, compared on a small thumbnail, so a still screen costs almost nothing; one frame
  every 5 s keeps the link proven alive.
- **Its own connection.** Frames go on a separate WebSocket at `/screen`, binary, so they can never hold up the control
  link. Never queue: while `ws.bufferedAmount` is high, frames are dropped and the newest goes next. A slow phone gets
  fewer frames, not older ones.
- **Frames are never written to disk.**
- **When the capture is impossible** (a UAC prompt, the lock screen, the secure desktop), the loop survives the error
  and the phone says „A képernyő most nem látható", then recovers by itself. Protected video may appear black.

## Who may see it

| Rule | Why |
|---|---|
| The relay was started with `--shots`, as for 📸 | Viewing stays off unless the user chose it. START → G stays without it. |
| A trusted link asks for a ticket (`screen.ticket`): random 128-bit, one connection, 60 s, sent in a header, never in the URL | The same rule as M12's board. A stranger on the WiFi gets nothing. |
| Removing the pairing cuts the stream at once | `relay-pair.js` already marks the live connections; `/screen` follows the same mark. |
| One viewer at a time | A second one is refused, and the answer names the phone that is watching. |
| The PC shows it clearly: a small always-on-top window, „A telefon látja a képernyőt: <telefon neve>", with a **Leállítás** button | Nobody at the PC should be watched without knowing. The window is part of the capture process, so it cannot outlive the stream or be left out of it. Every start and stop is logged on the relay console. |
| The stream stops when the view is left, the app goes to the background, the phone's screen turns off, or after 30 minutes | Nothing keeps running unseen. The phone offers „Folytatás" after the limit. |

## Build

- **Relay** (`tools/relay-screen.js`, tested alone like `relay-pair.js`): the capture process, the ticket, the `/screen`
  socket, the rules above. `RELAY_FRAMES_DIR=<folder>` plays numbered JPEGs instead of capturing, for tests and headless
  boxes, as `RELAY_SHOT_FILE` does for 📸.
- `kit-core`: the frame header and the viewer's state machine (connecting, live, not visible, stopped + the reason), with tests.
- `feature-screen`: the live image with pinch zoom and pan, keep-screen-on, a monitor / window switch, a low / high quality
  choice, and a small line with frames a second and KB/s.
- **Steering.** A Légegér strip on the view (hold to move, left and right click) uses Légegér's existing sender, through
  `kit`. M13 adds no new way of controlling the PC, and tapping the picture does not click.
- `Catalogue`: stage BETA at the end of the WP.

## Tests (cloud)

Node, `Mobile/tests/relay-screen.js`, with its own port and `RELAY_FRAMES_DIR`:
- without `--shots`, with an untrusted phone, or with a used or late ticket: refused;
- frames arrive in order; a second viewer is refused;
- the source stops with the last viewer and at the 30-minute limit (a shortened limit in the test);
- a removed pairing ends the stream at once;
- a slow client drops frames, and the relay's memory does not grow;
- no frame reaches the disk.

Kotlin: the frame header (short, corrupt, wrong length) and the state machine.
