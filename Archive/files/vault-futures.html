Vault futures

What to build on the Data Vault so that it still works in 2036: six paths, in build order. The rule behind all of them: keep the seams boring and standard, and let the clever parts plug in behind them, where they can be swapped out.

01The short answer

The rule

Stable seams, swappable organs.

What lasts ten years is boring: JSON files in git, ES modules, custom elements, JSON-RPC messages, SHA-256 and SSH signatures. The new things (CRDTs, WebAssembly components, generated screens, on-device models) are worth using, but only behind those seams, as optional tiers you can remove.

The biggest opening

The agent standards have settled.

MCP and AGENTS.md went to the Linux Foundation's Agentic AI Foundation on 2025-12-09. Agent Skills (SKILL.md) became an open standard the same month. The vault should speak these, so that any agent, not only Claude, can search it, read a cell and assemble a recipe.

Ownership

Proving it is yours is cheap.

SSH-signed commits and tags, an offline root key that vouches for each phone's key, and a signed SHA-256 manifest. In 2046 all of it still checks with git and sha256sum, without GitHub. The vendor routes (GitHub attestations, Sigstore) need Enterprise Cloud or an online log.

What to skip

No sync server, no framework.

Electric, Zero and PowerSync sync through a Postgres server; Jazz 2.0 is still alpha. For one owner and about 20 devices, the canonical store stays plain JSON in git with a small merge of our own. SQLite is a derived index, and a CRDT is used only for the few long texts edited on two devices.

03Six paths, in build order

Cost: S = one session, M = a few sessions, L = a work package of its own. Every first step is something a session can start in data-vault today.

1Agents

The vault speaks to agents

cost Sstandards settled

Turn the catalogue into a tool any agent can use: first a skill, then a small MCP server once the skill feels clumsy.

First step
  • .claude/skills/data-vault/SKILL.md: how to search cells, read one, assemble a recipe and run the checks.
  • Later tools/mcp.js: read-only, stateless, zero dependencies, over stdio. Tools: search_cells, get_cell, list_recipes, assemble_recipe.
  • propose_cell writes only to a drafts branch. Client cells are never returned.
Why it lasts
  • MCP and AGENTS.md belong to the Linux Foundation's AAIF since 2025-12-09. Skills is an open standard (Dec 2025) used by Claude Code, Cursor, VS Code, GitHub and others.
  • The MCP 2026-07-28 revision dropped the initialize handshake and session ids and added server/discover, so a thin stateless server is the direction the spec itself took.
Risk: the spec still moves (the next revision may rename things). Keep the server thin, with no SDK, so a change is an afternoon's work.
2Trust

Signed, mirrored, restorable

cost S–Mmature tools

Make every cell provably yours and the whole vault restorable without any vendor, before more of our work flows into it.

First step
  • SSH-sign commits and tags on the PC (gpg.format=ssh) and commit an allowed_signers file.
  • An offline Ed25519 root key, on paper in two places (a 2-of-3 Shamir split is optional). It signs trust/devices.json, so each phone's Keystore key is vouched for by the root.
  • tools/manifest.js: a sorted path → sha256 manifest per release, signed.
Then
  • Each year an archive set on an offline drive: git bundle --all, the dependency tarballs, the Node binary, the Android build kit and the APK key, plus a "read this with nothing" note.
  • One restore drill a year on a clean machine.
  • A second git home (the Backup bare repo, or a self-hosted Forgejo) and decisions kept in the repo, not only in issues.
Risk: a lost or leaked root key. The only defence is a rehearsed recovery, plus a rotation note signed with the old key. Not worth it now: git's SHA-256 object format (GitHub does not support it), GitHub attestations (Enterprise Cloud for private repos), Sigstore (needs its online log).
3Plugins

A host with a permission broker

cost Mweb-standardWebView details unconfirmed

Let cells run inside any host safely: the plugin asks for what it needs, and the host grants only that.

The shape
  • Plugins stay plain ES modules. The host runs each in a module Worker, with an SES Compartment (Hardened JavaScript) around anything an agent wrote.
  • Host and plugin talk JSON-RPC 2.0 over postMessage. The same broker works in a browser, in Node (worker_threads) and in the Android WebView.
  • UI is a custom element; untrusted UI renders in a sandboxed iframe with CSP connect-src 'none'.
needs becomes a contract 
"api": "^1.0",
"needs": {
  "storage": "own",
  "net": ["api.open-meteo.com"],
  "ui": "sandbox"
}

A missing key means denied; a pure function needs {}. The host enforces it, so the manifest is what you review when an agent writes a plugin. The model is taken from MV3 extensions, Deno, WASI and Tauri.

Risk: language-level isolation is weaker than WebAssembly (a runaway loop, engine bugs). Use Worker timeouts, and iframes for UI. On Android, keep plugins as data run by the WebView, never as downloaded DEX or .so: that keeps the app clear of the developer-verification and dynamic-code rules.
4Agents, screens

The request loop, with screens as data

cost M–Lschemas pre-1.0

You ask on the phone; an agent answers with a new cell. Either a plugin with its test, or a screen written as JSON that only uses components from our catalogue.

How it works
  • A Kérés note in a fixed shape (GO VARIANT, widened from Sketcher variants to anything).
  • The agent writes a screen spec that must validate against genome/screens.schema.json, a list of the shell's own components. The shell renders it.
  • An accepted spec is committed as a cell, so it is data from then on and doesn't change between runs.
  • origin records who made it: you, or which agent, model and session.
Why constrain it
  • Generated UI is good: in Google's study it came close to expert-made pages. Free-form HTML is where the danger is: in Veracode's Spring 2026 data about 44% of AI coding tasks introduced a flaw, and only about 15% of XSS cases were handled safely.
  • A catalogue-constrained spec cannot inject script, and keeps the Mélyvíz look. It also fixes the drift problem named in round 1.
Risk: A2UI (v0.9) and json-render are young, so borrow the idea and own the schema. Weak tests give false confidence: an agent may never edit the test of the cell it is changing.
5Data

Local-first sync without a server

cost Mlibraries activeOPFS in WebView unconfirmed

Once phones edit cells offline, give every device its own copy and a small merge of our own, with GitHub as the meeting place.

The shape
  • JSON in git stays the truth. Each device keeps a local copy and an append-only inbox (JSON Lines) of its edits, pushed when online.
  • Merge per field, last writer wins, per cell. One file per cell keeps conflicts rare.
  • Each cell gets a schemaVersion, migrations vN → vN+1 are tested against stored samples, and unknown fields are kept.
Around it
  • SQLite as a derived index and a .sqlite archive export: the official @sqlite.org/sqlite-wasm 3.54.1 (2026-10-19) in the browser, the platform SQLite in Kotlin.
  • A CRDT only for long texts edited on two devices: Automerge 3.5.0 (2026-09-16) or Loro 1.18.0 (2026-11-16), both MIT, with a JSON copy beside the binary.
Risk: the merge is our own code, so the bugs are ours too. OPFS and SharedArrayBuffer in Android WebView are unconfirmed: test on the real phones first (the IndexedDB fallback is slower but works). No Kotlin binding is confirmed for Automerge 3 or Loro.
6Data, agents

Search by meaning, AI on the device

cost S–Mphone models early

Find a cell by what it does, not by its name, and let the phone tidy notes without sending client words anywhere.

Search
  • harvest.js writes an embedding for every cell into one vector file; search is a plain cosine loop.
  • A few thousand records need no vector database. sqlite-vec is awkward in WASM, because extensions can't be loaded at run time.
  • EmbeddingGemma runs in the browser through Transformers.js. It is the one optional dependency, kept outside the zero-dependency core.
On the phone
  • The ML Kit GenAI Prompt API (Gemini Nano, alpha since Oct 2025) is a native Android API: VRG Mobile can call it, a web page cannot.
  • Chrome's built-in Prompt API (Chrome 148) and Summarizer (138) are desktop only, with no Android support found.
  • Uses: tidy dictated notes, caption site photos, draft a Kérés.
Risk: the model download and its dependency. Keep it optional, and keep the vectors rebuildable from the cells.

05Build order

  1. The skillOne file. Every later session, and any agent, uses the vault the same way.
  2. Signing and manifestDone before more content flows in. Needs your PC once, for the key.
  3. The broker hostMakes the three plugins, and every later one, runnable in a page and in the WebView.
  4. The request loopKérés → a cell. Screens as catalogue-checked JSON. This is where malleable starts.
  5. SyncWhen phones begin to edit cells offline, not before.
  6. Search and on-device AIWhen the catalogue passes about a thousand cells, or the phone needs it.

Alongside all six: lift one plugin-potency cell a week into plugins/, with its test. The recipes name which cells matter most: the Console widgets first, then the VRG Mobile kit modules.
