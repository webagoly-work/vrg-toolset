# 1.1 backlog — triaged

Read with `planner_1.0_review.md`. Every item is tagged:

- **SHAPES 1.0** — the schema must anticipate it or 1.1 gets expensive
- **RIDES ON 1.0** — needs the new model but doesn't change its design
- **INDEPENDENT** — could ship any time

---

## What this batch changes about 1.0

Three things move from "nice architecture" to **required**, and they're worth naming before Phase 2 starts.

### 1. Connectivity becomes a first-class model, not a by-product of geometry

Items R1, R2, R4, H2 all need to answer: *between these two boxes, what continuous routes exist, which conduits are on them, which wires are pulled through, and which circuit do those wires belong to?*

Today that only exists implicitly — paths are polylines and connectivity is "these two nodes happen to share coordinates". A mind-map editor cannot be built on coincidence. The schema needs, alongside the drawn geometry:

```
terminals   device | junction | board          (an id, a place, a purpose)
segments    a drawn run between two terminals  (geometry + profile)
runs        a wire/cable pulled through an ORDERED LIST of segments
circuits    a grouping of runs that belong together
```

The drawn polyline stays exactly as it is — this sits on top of it. But **occupancy** (what is pulled through what) has to be modelled, and today's `sec.circuit` single field can't carry it. This is the biggest single change your batch makes to the 1.0 design.

### 2. Ids and a shared selection stop being optional

P2, R3 and W1 all require selecting several things, keeping that selection while switching view, and having the editor and the planner highlight each other's selection. That is impossible with array indices — a splice in the planner would silently repoint the editor's selection at a different object. Stable ids and a model-level `selection` were already in the plan; this batch makes them load-bearing.

### 3. A validation layer needs a home

You described KSP-style flagging in four places: crossings and overlaps, a missing Betáp (orange), wires of one circuit split across separate routes, and empty path sections. That's a `validate(doc) → issues[]` module plus one place to display issues. Small to build, awkward to retrofit — so 1.0 gets the seam and one or two rules, and 1.1 fills the rule set.

## Queue

### P — Path drawing and consolidation

**P1 · Render toggle button (normal ↔ hivatalos) next to 2D/3D** — INDEPENDENT · small
Straight UI. Could even land during the refactor as a freebie.

**P2 · Ctrl+LMB multi-select of path sections → Összerendezés** — SHAPES 1.0 · large
Select runs between any two nodes; if they're reasonably close, pack them side by side into a single-depth arrangement so one chase serves them all. The reference section is either the first one selected or the one that was right-clicked.
*Needs:* stable ids, multi-selection, and a **bundle** concept — several logical runs sharing one physical chase, reversibly. Note this is the same primitive as the 1.1 cable-tray work: a tray is a bundle with a rectangular profile.

**P3 · Draw-time overlap ruleset: Backtrack / Snap / Ignore / Dedikált** — SHAPES 1.0 · large
Switchable **before each new section**, mid-draw, from the floating display.
My reading of the four modes:
- **Backtrack** — retracing an existing run adds no new geometry; the wires simply also travel that run
- **Snap** — the new run offsets beside the existing one at the same height, auto-aligned, ready to share a chase
- **Ignore** — draw freely; crossings and overlaps are still flagged
- **Dedikált** — force a genuinely separate run even where it coincides, and never auto-merge it later

*This is the item I'd most want to talk through before building* — see the open questions below.

**P4 · Paths are dedicated circuit runs by default** — SHAPES 1.0 · design decision, no code of its own
The consequence: merging is an explicit, reversible, recorded act — never an automatic side-effect of geometry. This is a rule the whole model must obey, which is why it belongs in the schema rather than in a feature.

**P5 · Two-point pathway adjustment** — RIDES ON 1.0 · medium
Select two terminals → set how many conduits of what type run between them for the wires needed, and how wires are soft-chained when they share a circuit. Splitting one circuit's wires across separate routes stays legal but gets flagged.

### R — Rendezés editor (the mind-map)

**R1 · The graph editor itself** — RIDES ON 1.0 · very large
Abstract bubbles-and-lines view: one line per drawn path, colour-coded wire lines beneath it. Whole-system view of everything hanging off the Elosztószekrény, or focused on two selected points plus every intermediate box and merged section.
*Note:* this is the fourth thing that is "a projection of the model with a selection and an edit layer" — after the wall elevation and the three plan planes. If the SurfaceEditor abstraction from Phase 3 is done right, this is a new projection rather than a new editor.

**R2 · Wire editing inside it** — RIDES ON 1.0 · large
Place wires on lines, chain them into circuits, duplicate parallel pathways, add wires singly / in common bulk configurations / from device requirements. *Behúzás* once the counts are right. New connections must be drawn in the planner first — the editor only shows continuous end-to-end routes.

**R3 · Two-way highlight between editor and planner** — SHAPES 1.0 · medium
Select in the editor → it lights up in the planner, and vice versa. Ctrl+LMB multi-select in the planner → already selected when the editor opens → "focus" hides everything else.
*Needs the shared selection model.* This is the feature that most repays getting ids right.

**R4 · Betáp rule** — RIDES ON 1.0 · small
With the Elosztószekrény toggled out of view, one selected box must be marked Betáp; otherwise flag orange (medium severity). First customer of the validation layer.

**R5 · Open in a separate window** — SHAPES 1.0 · medium
Straightforward *only if* editors don't depend on the one global modal element. Cheap to allow for in Phase 3, expensive to retrofit — so the editor gets a mount target rather than a hard-coded container.

### W — Alignment in the 2D editors

**W1 · Rendezés for wall/floor devices** — RIDES ON 1.0 · medium
Rubber-band or Ctrl+LMB select loose szerelvénydoboz and devices, then align vertically or horizontally. Vertical: the topmost device's height defines the series and the rest build downward.
*Note:* the existing clip mechanism (72 mm spacing groups) already does the placement maths — this is mostly selection plus a "distribute" command on top of it.

### H — Help and navigation

**H1 · Súgó tool** — SHAPES 1.0 (cheaply) · medium
Works like the format painter but for help: click any element, any UI button, any sidebar box → the help panel opens with everything relevant, sorted by relevance.
*This is nearly free if the action registry lands, and painful otherwise.* Every action already needs an id and a label for the registry; adding a `help` key makes this a content-writing job instead of a plumbing job. Same for model concepts.

**H2 · Cable-tool hover readout** — RIDES ON 1.0 · small
Hover a path or device with wires connected to a board → the floating display shows wire count and circuit. Hover a kötődoboz → every cable and wire currently passing through it.
*Trivial once occupancy is modelled; impossible before.*

## G — Controller, what phase 1 deliberately left out

Phase 1 covers the main stage: camera, cursor, placement, selection, dragging, height stepping,
the wheel and the legend. These are the edges it does not reach, in the order they are worth doing.

**G1 · The wall and plane editors** — RIDES ON 1.0 · medium
The editors are a second interaction model with their own drag, warp and session rules, and the
driver currently stands down when `edCur()` reports one open. `edBindSurface`'s `local(ev)` takes
client coordinates, so the same synthetic-event approach should work — a surface descriptor gets a
cursor the same way the stage did. Wants its own legend, because the verbs are different in there.

**G2 · Dialogs and the palette** — INDEPENDENT · medium
Today Start opens the ⌘K palette and the stick cannot drive it. Form-field navigation is the one
place a controller is genuinely worse than a keyboard, so this is worth doing for the *list*
surfaces (palette, project list, lamp picker) and probably not for the numeric property sheets.

**G3 · Per-profile bindings** — INDEPENDENT · small
The binding table is one object in `08b-gamepad.js`. Making it data the settings panel can edit is
mostly UI work, and worth it the moment a second person uses a controller with different habits.

**G4 · Wheel commit on release** — INDEPENDENT · trivial
Tropico committed a radial pick on *release*, which is a little faster than press-to-confirm. Half
of this exists (hold Y, release on a sector, descend); extending it to the sub-ring means one timer
and a setting, and it should be a setting — it is a real preference, not an obvious improvement.

**G5 · Non-standard pads** — INDEPENDENT · small
Everything assumes `mapping: "standard"`. A pad that reports an empty mapping string has its own
button order and would need a remap table, or at minimum a warning in the settings panel.

## Open questions (not blocking — answer when we reach P3/R1)

1. **Dedikált vs Ignore.** Is Dedikált "never merge this, even if I later run Összerendezés over it" — i.e. a permanent property of that run rather than a draw-time mode? That's how I've assumed it.
2. **Backtrack and wires.** When a run backtracks over itself, the geometry doesn't duplicate — but do the wires? In your example the switch drop returns to K2 along the same line: is that one conduit carrying more wires, or two conduits in one chase? The answer decides whether Backtrack is a geometry rule or an occupancy rule.
3. **"Reasonably close" for Összerendezés.** A fixed mm threshold, a multiple of the chase width, or a value you set per operation?
4. **Bulk wire configurations.** Which three or four are worth a one-click button? (My guess: 3×1.5 lighting, 3×2.5 socket, 5×2.5, and whatever your standard for a switch loop is — correct me.)
5. **Cross-circuit soft-chaining.** When wires of one circuit take separate routes, is that a warning or an error in your practice?

## Suggested order once 1.0 ships

1. **P1** — trivial, immediate value
2. **P3 + P4** — the drawing ruleset, because everything downstream depends on what a path *means*
3. **P2** — Összerendezés, sharing the bundle primitive with P3's Snap mode
4. **W1** — same selection work, small addition
5. **R1 + R3 + R4** — the Rendezés editor as a projection
6. **R2 + P5 + H2** — the wire/occupancy layer, all three at once since they're the same model
7. **H1 + H3** — help and navigation, once the registry is populated

One structural warning: **P3's Snap mode and P2's Összerendezés must share one implementation.** They're the same operation at different times — one while drawing, one as cleanup. Built separately they will disagree about spacing within a month.
