## 2. Findings from the analysis (root causes — read before touching the area)

**F1 · Select tool "does nothing" (item 7).** `08-interaction.js` pointerdown, `state.mode==='select'`
branch (≈ line 112): a hit sets `selected=h` and `dragItem`, then **returns without `draw()`**; pointerup
does not draw either. The inspector is re-rendered only from `draw()` (`renderShell(true)` at the end
of `04-render.js` `draw`), and the overlay draws a highlight for a *single* selection **only in grab
mode** (`gizmoSvg`, 04-render ≈ line 984) — select mode highlights only multi-selections. So the
selection exists but is invisible until something else redraws (switching to Move does). Second,
smaller defect in the same branch: any pointer movement after the click drags the piece (no
threshold) and pushes an undo step — a slightly shaky click moves the item.

**F2 · Misclick on the blue centre (item 8).** The gizmo's centre dot (`12-boot.js` `gizmoSvg`,
`<circle … r="3.5">` near the end) has **no `class="giz"`**, so a click on it falls through to
`hitTest()`, which picks the nearest *centre* among all pieces — another piece wins whenever its
centre is closer. In addition `hitTest()` (09-menus line 10) lets objects claim a radius of half their
footprint (`rad`) and **resets `hd` to their distance**, so a big object near the cursor shadows
smaller pieces; and nothing gives the already-selected piece priority.

**F3 · Hidden things are clickable (item 9).** `hitTest()` and `devHitIdx()` (09-menus) check only
`lyrLockHit` (lock), never `layerShows()` (layer + sub-layer visibility). Openings, devices, notes and
cables do not even check `state.levels`. `finishSelBox()` (08) checks levels only. `lampAt()` (10-lamps)
and the device right-click (`10-lamps.js` ≈ line 382, via `devHitIdx`) inherit the same gap. Draw-time
filtering (04-render) uses `state.levels[...] && layerShows(item,cat) && soloOk(...)` — the hit side
must use the same predicate.

**F4 · "Falak egyesítve" (item 4).** See §3 — it works, but only in one wall mode, which is not the
default.

**F5 · Tab is already taken.** Five stack tools use Tab: RBX class cycle (`05p` hwPlace), endpoint
variant cycle (`05s` epPlace), channel rule and ARM rule (`05r`, `05u`), mark-plane floor↔ceiling
(`05n` line ≈ 574). The help dialog and hints mention Tab in each. U4 moves them (MATERIAL §1).

**F6 · WASD/QE are captured.** In Move (grab) mode with a selection, W/A/S/D move and Q/E rotate the
piece (08 line ≈ 332); in Select mode a selected **object** is moved by WASD/QE (≈ line 355); the
Object tool's ghost rotates on Q/E (≈ line 351). Everywhere else WASD pans and Q/E zoom (≈ line 364).
That inconsistency is what the user feels.

**F7 · Moving a device never moves its linked route nodes in plan.** `wvPushLinkedNodes()` exists
(06-wall-editor line ≈ 532) but is called only from the Wall View / Plane View editors. Plan-view moves
(select drag in 08 ≈ line 232, `pSetC` in 12-boot line 61, WASD nudge) leave golden (`route:'channel'`)
and silver (`route:'arm'`) route ends behind. Routes attach to hardware through `dev.links`
(`hasLinkTo`, `chnDevAt`), so the data to follow already exists.

**F8 · BASE + RBX on one wall section is already allowed by the model.** `hwGhostAt('rbx', level,
base.x, base.y)` on CLA-teszt v2 returns a valid ghost at the BASE's spot (measured: BASE 0–1800 mm,
RB-M 1900–2400 mm — no vertical overlap). Whatever stops the user is in the *plan* (two symbols drawn
on the same point, one hiding the other and stealing its clicks) or in the click path, not in a rule.
S3 starts by reproducing it in the browser.

**F9 · Wall notes are keyed by wall coordinates.** `wallKey(r,level)` (06-wall-editor line 191) is
`level:x0,y0,x1,y1` rounded — any change to a wall rectangle orphans its `data.wallNotes` and
`data.noteHide` entries. Marks (`05n`) store an along-wall `u` measured from the wall's **start**
(`mrkU`), so moving a wall's start end shifts every mark on it. G2 must re-key and re-offset both.

**F10 · Openings are a zero-thickness face.** `pushOpening()` (04-render line ≈ 680) draws one
vertical quad on the wall centreline, so from above a door or a window is a line. The blueprint
already knows each opening's host wall span (`bpWallSpans`, 04-render line 259) — G1 reuses it.

**F11 · Small discrepancies found on the way** (not in any WP — tell the user): RB-S depth is 90 mm
in BRIDGE-ARCH-002 / CLA Inline Architecture but 110 in `HW_RB`; `ELO_RULES.lightPerRbx` still counts
one lighting way per RBX while the user's rule is one string (already in the 10-09 handover).

## 3. Answer to item 4 — what "Falak egyesítve" does

**What it is for.** It draws the walls of a level as **one body**: where two wall rectangles overlap,
the faces that fall inside the other wall are dropped (`faceBuried`, 04-render ≈ line 495), and seen
from straight above (pitch ≥ 88°) the outline is drawn once around the union instead of once per
rectangle (`rectsUnionSegs`). The walls stay separately selectable. The blueprint view always draws
this way.

**Why it seems to do nothing.** `drawNormalGeom()` gates it with
`const merge = wallMergeOn() && wm === 'solid'` — it acts **only when View → Walls is "solid"**. The
default is "translucent", and on CLA-teszt v2 the scene is byte-identical with the box ticked or not
(measured: 113 082 characters both ways; solid + merge 107 584, solid alone 111 638). In translucent
mode the overlap squares at the corners show darker (picture 3) — exactly what merging would remove.

**Fix (U7).** Let the merge act in translucent mode too — and, because the burying test looks at a
face's centre only, also clip the overlapping top faces and partly-buried side faces so every plan
point is painted once (walls are axis-aligned, so this is rectangle subtraction). Then the darker
corner squares disappear. In "hidden" mode grey the checkbox out with a tooltip. Nothing changes in
any golden render (they render the default, merge off).
